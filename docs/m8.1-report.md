## Implemented scope

M8.1 implements only the typed proposal foundation frozen by M8.0:

- typed proposal, recommendation, status, and evidence-state registries;
- database constraints for proposal scope, lifecycle values, evidence states,
  allowlisted recommendations, reviews, and idempotency records;
- tenant/factory and completed-source-run binding;
- `POST /api/v1/agent/runs/{run_id}/disposition-proposals` for authorized,
  server-constructed drafts;
- `GET /api/v1/disposition-proposals/{proposal_id}` with self/tenant
  authorization and resource hiding;
- exactly one bounded `Idempotency-Key`, deterministic request hashing,
  same-request replay, and different-request conflict;
- cross-type recommendation rejection and duplicate-action rejection;
- server-assigned draft identity, version, creator, 24-hour expiry, and
  `inconclusive` initial evidence state; and
- sanitized authorization-decision auditing for proposal endpoints.

M8.1 does **not** let an Agent generate or submit a proposal. It does not
implement human approval/rejection, proposal execution, or writes to MES,
ERP, PLC, equipment, inventory, quality, work-order, or material state. The
material-discrepancy type is a bounded investigation record, not a claim that
the current datasets can identify “reported A, used B.”

## Decision

M8.1 passes because its typed draft model and create/read boundaries work in a
real PostgreSQL transaction, preserve tenant/factory and source-run scope, and
do not regress either mandatory dataset track.

M8 as a whole is **not complete**. M8.2 evidence-bound Agent generation, M8.3
human submission/review, and M8.4 adversarial/formal evaluation remain
pending and must pass without weakening the no-execution boundary.
