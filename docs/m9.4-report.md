## Implemented scope

M9.4 implements simulation policy `m9.4.v1`:

- `POST /api/v1/action-plans/{plan_id}/simulate` with M7 authentication,
  `simulate:action_plans`, creator ownership, `Idempotency-Key`, and positive
  optimistic `If-Match` version;
- simulation only from the `validated` lifecycle state;
- mandatory rebuild and equality check of the M9.3 canonical snapshot;
- fail-closed drift invalidation before any simulation is recorded;
- server-owned deterministic seed `9400001` and stable canonical input/output
  SHA-256 hashes;
- bounded affected-resource references, precondition findings, explicit
  missing-data findings, required human roles, and impact-preview entries;
- append-only `action_plan_simulations` and sanitized simulation audits;
- protected-state equality check inside the simulation transaction; and
- idempotent success/drift replay plus incompatible-key and stale-version
  rejection.

## Isolation evidence

The PostgreSQL integration suite hashes the source proposal, reviews, proposal
evidence, plan targets/evidence/steps, machines, work orders, production
records, downtime events, and quality inspections before and after simulation.
The hashes remain identical. The simulator independently rebuilds the M9.3
trusted-state hash before commit and persists `protected_state_unchanged=true`.

Simulation changes only M9 plan lifecycle metadata and append-only M9
simulation/audit/idempotency records. It does not mutate dataset records,
source proposals/reviews/evidence, MES operational tables, inventory,
genealogy, quality decisions, equipment state, or external systems.

## Explicit boundary

A completed simulation is an impact preview, not a prediction guarantee and
not evidence that a physical action occurred. M9.4 does not implement
submission, independent plan review, approval, rejection, cancellation,
execution, external export, ticket creation, notification delivery, or any
MES/ERP/QMS/WMS/PLC write.
